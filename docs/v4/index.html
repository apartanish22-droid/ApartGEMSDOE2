3. Why did GEMSDOE32 reach 0.2778, and can a file beat it?

What we verified (local bytes, not an organizer receipt):

  • The GEMSDOE32 file (37,654 dots) is an exact subset of the GEMSDOE30 file (44,090 dots). The 6,436 dots that were removed all lie within 3 px of the USGS/INGENIOUS catalogue.
  • GEMSDOE30 has 8,607 dots within 3 px of the catalogue. GEMSDOE32 has 2,171.

Mechanism (from the official metric definition, not measured): The problem page says the hidden test set is new faults that are not in the USGS database. A dot on a catalogue fault therefore has a distance to the nearest hidden truth pixel that is usually greater than 3 px. Its false-positive weight is then close to 1 (p·[1 − k]). Removing catalogue-near dots lowers the false-positive term (α = 0.2). This holds only if the hidden faults lie more than 3 px from the removed dots, which the problem page implies but does not state. The owner-reported gap (0.2778 vs 0.2600 for GEMSDOE30) is consistent with this. It is not proven, because the hidden labels are unknown.

Can we beat 0.2778? Not demonstrated. The obvious next experiment is catalogue pruning applied to the v4 ridge candidate. To keep it honest, pruning must use only the west-half labels, and the east half must be used only for scoring. That experiment was not run, because the protocol budget was spent (see section 6).

Sources: problem page (metric, hidden-fault definition) · GEMSDOE32 owner page ("already submitted")

5. Irregularities flagged for review

  1. Leaderboard figures in the brief do not match the official page (section 4).
  2. All 72 directed pairs among the nine focus rasters exceed 70% overlap. No focus-site file is unique relative to the others. The owner pages say the same (for example GEMSDOE36).
  3. SHA-256 mismatch: five owner files (GEMSDOE24, 25, 27, 28, 31) have different hashes from our local copies. We fetched the owner's files at the commits the owner page cites. Each owner file is the NaN-outside encoding of the same raster. After NaN→0 the values and positive-cell counts are identical (60,069; 44,090; 61,328; 37,660; 40,199). This is an encoding difference, not a content difference.
  4. Format risk: the official rule says data outside the bounds is null or NaN. Several historical files (GEMSDOE32 and others) use zeros outside. The brief's "Predicted values must be in range [0, 1]" error was reported, but we do not have the rejected bytes. Its cause is not diagnosed here. The v4 file follows the sample's NaN-outside convention.
  5. Lattice gate is not discriminating: LATTICE_r13 (206,895 dots, 5 px regular grid) covers 99.87% of the footprint within 3 px, so the literal 70% test fails for any dense file. This needs a rule decision, not a silent exemption.
  6. Protocol deviations in this session: the surface check against the registry was not run before dot placement; the q grid's optimum sat at its upper edge (q = 0.05) for all three experiments, so the true optimum may be higher; the budget of three experiments was spent.
  7. Data provenance: the training features and labels are owner mirrors on GitHub (hash-verified against the pins). They are not organizer-authenticated. The DrivenData data tab is login-walled, and the Dropbox links in the brief are not reachable from this sandbox.
  8. Shared tools: the pinned scripts/evaluate_holdout.py and scripts/submission_writer.py are unchanged and still have the open upstream defects listed in the README. The v4 code uses the official-form metric in src/gems32/metric.py instead. It is verified against the brute-force reference in tests/test_v4_candidate.py.

7. How to submit when a file is cleared (for future use)

Only follow these steps for a file whose run card shows verdict: promote, a clean uniqueness pass, and a separate selector approval. None of the files above qualifies.

  1. Open the competition page and click New submission.
  2. Upload one single-band GeoTIFF (.tif), or a .zip with one GeoTIFF. CRS EPSG:32611, 3,730 × 3,292, 100 m, same bounds as the training data.
  3. Values must be float32, inside [0, 1], and NaN (or null) outside the bounds. Check the saved bytes with the validator before uploading.
  4. Enter a unique name and a note of at most 140 characters.
  5. Record the organizer's receipt (the submission page) with the file SHA-256. Only that receipt makes a score ORGANIZER-CONFIRMED.

Official format: problem page, submission format.

8. Limitations and next steps

  • Proxy, not score: every estimate here uses catalogue labels. The hidden test set is new faults, so the proxy can mislead in either direction.
  • Next experiment (E4): west-tuned catalogue pruning of the ridge candidate, scored on the east half against the same reference. Pre-register it first. This is the only path that tests the GEMSDOE32 mechanism without leakage.
  • Next experiment (H2): tilt zero-contour consensus, pre-registered and run under the same protocol.
  • Data: get the authenticated DrivenData files (training features, labels, DEM link list). Until then every number is a mirror-based proxy.
  • Rule decision: the lattice gate must be fixed by the rule owners (a dot-count-aware or null-calibrated version). Until then no dense file can pass it.
  • Owner receipts: ask the owners of the nine focus sites for their organizer receipts, which would make their scores ORGANIZER-CONFIRMED.
