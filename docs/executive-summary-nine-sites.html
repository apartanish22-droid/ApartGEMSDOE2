Why GEMSDOE32 scored highest (0.2778) — and is >0.2778 reachable?

  1. What is verified. GEMSDOE32 B2 has 37,654 dots. It is an exact subset of GEMSDOE30 (44,090 dots) and of GEMSDOE31 (40,199 dots), checked cell by cell. The 6,436 dots removed from GEMSDOE30 all lie within 2 px of the known-fault catalogue (existing_faults.tif; 3,891 within 1 px; none farther). This is the only structural difference the repo can show.
  2. What is not verified. The 0.2778 score itself. It is user-reported with no receipt. Organizer masking of known faults is unresolved (see Limitations), so the mechanism is a hypothesis, not a proof.
  3. What our proxy says. Removing near-catalogue dots (E1, B2) gives a holdout gain of +0.00072, 95% CI [+0.00034, +0.00117]. Random thinning to the same count gives 0.03387, so the gain is explained by density. This is much smaller than the jump from 0.2600 (GEMSDOE30) to 0.2778 (GEMSDOE32). The proxy therefore does not reproduce the claimed mechanism.
  4. Is >0.2778 reachable? Not shown. Our three experiments are negative: the v4 ridge ranking scores below random placement at matched budget (E2), spatial clustering does not explain that (E3), and near-catalogue removal is density-equivalent (E1). Higher scores have been reported on the public leaderboard (repo notes record 0.4544 at rank 1, observed 28 and 30 Oct 2026, and 0.3916 at rank 2, observed 28 Oct; none verified here). The method that gets there is unknown to us.

How to submit (for the selector — not an instruction to upload)

  1. File: single-band GeoTIFF (or a zip of one), EPSG:32611, 3730 × 3292, 100 m, geotransform (243350, 100, 0, 4508550, 0, −100) — as in the official sample.
  2. Values must be in [0, 1]. Prior upload error: "Predicted values must be in range [0, 1]".
  3. Unique name and a note of at most 140 characters.
  4. Pass every gate (uniqueness vs the full registry, holdout vs random control, checker). No file currently does, so there is nothing to upload.
  5. Weekly cap: shown on the submission page. The selector step is separate from this research and no slot has been used.

Untried hypotheses (ranked, unvalidated)

Four candidates with layers, physical signatures, mimics, costs and data status are in docs/research/v5-hypotheses-20261031.md. Rank 1 is H5-A, hydrothermal magnetic-low troughs (layers tmi, rtp). Its physical basis is supported by the USDOE/OSTI Coso aeromagnetic report, which attributes a magnetic low to magnetite destruction by hydrothermal solutions. None of the four has been run.

Limitations and irregularities

  • No live leaderboard check. DrivenData and community.drivendata.org are unreachable from the sandbox.
  • Prompt leaderboard conflict: the prompt cites 0.4413 and 0.3195 as current highs. Repo notes (30 Oct review, top-50 snapshot) record 0.4544 at #1, report 0.3195 at #48, and say 0.4413 does not appear. None of this is re-verified live from this sandbox.
  • Known-fault masking is unresolved. The organizer thread that would settle it is unreachable.
  • Gate rule vs implementation: the rule says rank-correlation; the gate computes Pearson correlation. For binary dot fields the two are close, but they are not identical for the float fields.
  • Registry: 489 rasters compared. One (GEMSDOE36 format test, 32×48) is a different grid and is excluded from the gate, as recorded in the uniqueness JSON.
  • Official reference notebook (drivendataorg/gems-prize-reference-solution, unet-mc-cv-reference-solution.ipynb): the raw file returns HTTP 302 to a host outside the sandbox allowlist, so its submission-writing convention is unchecked.
  • The "[0, 1]" rejection is not reproduced: all in-footprint values in the files tested are inside [0, 1]. The bytes of the rejected upload are not in the workspace.
  • The pre-existing GEMSDOE32 explanation and the metric documentation disagree on whether near-catalogue dots are penalised. This is open.
