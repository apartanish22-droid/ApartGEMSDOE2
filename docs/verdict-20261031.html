3. Why did GEMSDOE32 (0.2778) score highest? (verified mechanism, not a proven score cause)

  • Verified (bytes): GEMSDOE32's best file (37,654 dots, binary 0/1 values) is a strict subset of GEMSDOE30's file (44,090 dots). The 6,436 dots removed from GEMSDOE30 are 6,436 of 6,436 within 3 px of the USGS/INGENIOUS catalogue. Only 2,171 of GEMSDOE32's 37,654 dots (5.8%) sit that close.
  • Owner-reported difference: 0.2778 (GEMSDOE32) versus 0.2600 (GEMSDOE30), +0.0178. Neither is an organizer receipt.
  • Hypothesis (labelled, not measured): the hidden test set is new faults that are not in the catalogue. Dots that sit on known catalogue faults are then likely false positives, and removing them reduces false positives on the hidden set. The recall cost of removing them is not measured here. A receipt-free test: remove catalogue-adjacent dots from a fixed base and measure the off-catalogue proxy and its recall cost.
  • Why the repo's own holdout does not show it: the hide-and-recover proxy rewards catalogue recovery. GEMSDOE32 scores 0.0045 there, below the random-dot null of about 0.032. That proxy is therefore anti-aligned with pruning and cannot rank these files.

4. Why the portal said 'Predicted values must be in range [0, 1]'

  • Verified (bytes): the user-named -nan files for GEMSDOE24, 25, 27, 28 and 31 each carry 7,111,787 NaN cells outside the footprint. The user-named files for 30, 32, 33 and 36 carry none. For all nine sites, the dot set inside the footprint is identical to the pinned zeros copy.
  • Hypothesis: the portal's [0,1] check fails on NaN. That is consistent with the error, but the portal itself has not been tested from here.
  • Practical fix to try: use the zeros-outside copy of the same dot set (table above). It satisfies [0,1] and has no NaN.
  • Rule conflict (flag for review): the official rules say data outside the bounds is 'null or nan' (rules PDF, https://www.drivendata.org/competitions/306/competition-doe-gems/page/967/). A zeros-outside file is not literally 'null or nan' outside. Only an organizer answer can settle this; a forum question is the right channel.

5. Why no dense file can pass the literal uniqueness rule

The 13GEMSDOE lattice raster (r13-lattice-s5, 206,895 dots on a 5-px grid, in the 13GEMSDOE repo) covers 99.87% of the 5,167,373-cell footprint within 3 px. Only 6,649 cells lie farther than 3 px from every lattice dot. The 70% rule needs at least 30% of a file's dots to lie in those cells, and each cell holds at most one dot, so the file has at most 6,649 such dots. Therefore the total is at most 6,649 / 0.30 = 22,163 dots in total. Every file above that size fails the literal rule by construction, including all nine sites and both S31 files. Sparser files can satisfy the bound. The best sparse record in this repo (H-SARPU, HOLDOUT-DTI 0.1138 [0.1000, 0.1271], evidence/sarpu_run_card_20261028.json) is well below the bar.

Decision needed (for you, not a manual step in the pipeline): does the 13GEMSDOE lattice count as a 'registry raster' under your 70% rule? If it does, the rule cannot be met by any file with more than about 22,000 dots. If it does not, the 37k–52k-dot S31 files pass the overlap test (about 0.68), and the copy question in section 2 becomes the deciding one. The repo has a null-calibrated option for space-filling rasters (space_filling_coverage, src/gems32/registry_audit.py); the official rule text does not provide it, so using it would be a governance choice.

The mirrors are SHA-256 pinned but not organizer-authenticated, so any final check should use an official download from your own DrivenData account.

  3. 0.4413 does not appear in ranks 1–50 of the fetched board.
  4. Owner overlap label is imprecise. The GEMSDOE28 S31 page gives 0.6800 as far65's worst overlap against the nine-site registry. Our nine-site worst for far65 is 67.29% (GEMSDOE27). The 68.00% figure is the full-registry worst excluding the lattice (GEMSDOE32 h47), a different set. The owner's 0.6688 versus the 0.2778 parent matches our 66.88%. Our nine-site worst for midband is 68.00%.
  5. Owner pages say 'already submitted'. GEMSDOE32's page says its 0.2778 file is already submitted. No receipt is archived here.
  6. Holdout proxy is anti-aligned. On the hide-and-recover evaluator the best reported file scores 0.0045, below random dots. Its known split defect is that 15,705 of 22,232 withheld positives lie within 15 px of visible faults.
  7. Registry refreshed. registry/focus_registry_manifest.json now lists 511 rasters (was 489, none removed). The 22 additions are dated 28–31 Oct 2026: GEMSDOE27 (11), GEMSDOE24 (5), GEMSDOE25 (3) and GEMSDOE28 (3). They enter the uniqueness gate but were not individually scored here.

7. What would produce an OK-to-submit file

  1. A decision on the lattice rule (section 5), and a decision on whether the portal accepts zeros-outside files (section 4). Both are governance questions.
  2. Training data from your own DrivenData download, placed in data/, replacing the mirror.
  3. A new method, pre-registered, with a catalogue-free or pruning-aware proxy on the authenticated data and a paired confidence interval against the same-evaluator baseline. A file that only beats the proxy by overlapping intervals is not enough.
  4. Full 511-raster gate on the final bytes, and a single format-test submission to see whether the portal accepts the zeros-outside encoding.
